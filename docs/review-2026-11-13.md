## Administration and Guideline 11

The [directory guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/)
were checked against the actual output and hooks:

* Sponsor, Speo, voluntary donation and review links are confined to the
  plugin's own settings pages. They do not load remote assets or track clicks.
  No incentive, payment or review gates an included function.
* The native Dashboard widget contains operational statistics and a local
  settings link. It is limited to administrators and respects WordPress's
  Screen Options preference. It contains no promotional request.
* Integration notices appear only on recognized provider or relevant Core
  screens, subject to their native permissions and an enabled, available
  integration. Their purpose is to explain protection and where spam is kept.
* The installation-conflict error disappears when the conflict is resolved.
  Statistics-upgrade errors preserve existing records; the new help explains
  how to retry and which hosting checks are useful if the retry fails.

In 0.5.5, each user can persistently hide contextual protection notices on the
current website and restore them from Integrations or their own profile.
The controls change display preferences, not protection settings. Native
per-site user options keep accounts and multisite websites separate. The
profile control also serves moderators who cannot access plugin settings.

The notice keeps its script-free POST form through a narrow local KSES
allowlist. Core's `wp_admin_notice()` uses the post-content allowlist, which
removes form controls; its documented
[wp_get_admin_notice renderer](https://developer.wordpress.org/reference/functions/wp_get_admin_notice/)
is therefore used
before applying this plugin's explicit allowlist. No global KSES rules or
provider files are changed.

The new preference nonce uses its own field name,
`rktsky_antispam_notices_nonce`. It does not duplicate the `_wpnonce` ID used
by native provider editors or `options.php`. The verified Core notice/header
hooks run before the CF7, Gravity Forms and WPForms page forms; no footer form
or provider-source patch is needed.

## Authorization, nonces and escaping

The review's general security guidance did not identify a specific vulnerable
line. The existing handlers and output paths were checked rather than adding
authorization to unrelated public endpoints:

* The four existing administrative POST handlers require `manage_options`,
  POST and a matching native nonce before mutation. Settings use WordPress's
  Settings API and `options.php`; their REST exposure remains disabled.
* Provider moderation keeps native provider permissions. Feedback handlers
  retain authorization for the corresponding native entry or administration.
* Public challenge endpoints intentionally serve anonymous forms. Their
  bounded, authenticated scope cannot change settings or create an entry;
  requiring administrator permission would prevent their intended use.
* Raw helper output was traced to its escaped field/control templates.
  Quarantine content and URLs retain context-specific escaping. No new
  unescaped visitor content was found in the inspected paths.
* New notice preferences require a logged-in POST. The nonce binds the site,
  canonical provider list and server-resolved native capability; the handler
  checks the current capability and current integration availability again.
  Restoration affects only the current account and current site.

WordPress's [nonce](https://developer.wordpress.org/apis/security/nonces/)
and [escaping](https://developer.wordpress.org/apis/security/escaping/)
contracts remain the basis for these checks. A nonce does not grant permission.

## Languages, package contents and activation guidance

The bundled German, French, Italian and Spanish catalogues are retained as
installation fallbacks. Native WordPress.org language packs take priority;
the fallback uses the documented
[lang_dir_for_domain filter](https://developer.wordpress.org/reference/hooks/lang_dir_for_domain/).
WordPress's [localization documentation](https://developer.wordpress.org/plugins/internationalization/localization/)
supports both local catalogues and centrally managed translations. The review's
translation advisory was not treated as a requirement to remove these languages.

Headers retain the actual minimums of WordPress 6.6 and PHP 8.2. Provider
availability and encryption requirements remain checked. Activation uses
the native lifecycle and the existing per-site table prefix, charset/collation
and `dbDelta` contracts. There is no new table or schema version in 0.5.5.
Existing settings, storage identifiers, tokens and retained records stay intact.

Notice preferences use native
[user-option](https://developer.wordpress.org/reference/functions/get_user_option/)
and [metadata](https://developer.wordpress.org/reference/functions/delete_metadata/)
APIs. When configured to delete plugin data,
uninstall removes only the current site's exact preference key; retaining
plugin data also retains preferences. Multisite site deletion removes only
that site's key without deleting users or another site's preferences.

The directory ZIP is built from committed source with readable owned source,
GPL-compatible licence information and no tests, tools, vendor packages,
private evidence or internal documentation. Assets remain screen-scoped.
No activation-time call to an external spam service is introduced.
